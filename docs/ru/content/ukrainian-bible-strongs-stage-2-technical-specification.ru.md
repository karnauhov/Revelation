## Статус и область

Этап 2 фиксирует технический контракт для утверждённого на этапе 1 перевода.
Эта спецификация является нормативной для этапов 3–12.

После первоначального закрытия этапа владелец добавил обязательное требование:
сохранять печатные сноски в отдельном комментарии к соответствующему стиху,
редактировать их в content tool и показывать в приложении. Поэтому этап 2
был переоткрыт. Baseline, таблица идентификаторов, генератор и contract-тесты
синхронизированы с описанным ниже schema contract версии 4; этап повторно
закрыт. Зафиксированные входные файлы этапа 3 не изменились.

В рамках этапа 2 не загружались и не фиксировались украинские исходные файлы,
не создавался украинский корпус и не собирался итоговый SQLite-модуль.
Эталон построен только из уже существующих локальных контрактов приложения:
`web/db/bible_kjv.sqlite`, `web/db/bible_lxx_tr.sqlite`,
`assets/data/bible_verse_map.json`, runtime-кода, сборщиков и редактора
контента.

## Утверждённый перевод и ограничения

Нормативный выбор:

- полное название: **«Біблія або Книги Святого Письма Старого і Нового
  Заповіту», переклад Івана Огієнка**;
- точная редакция: **юбилейное издание 1988 года**;
- охват: полный Ветхий и Новый Заветы;
- канон издания: 66 книг в протестантской последовательности;
- лицензия производного текстового/Strong-модуля:
  **Creative Commons Attribution-ShareAlike 4.0 International**,
  <https://creativecommons.org/licenses/by-sa/4.0/>;
- разрешение: Украинское Библейское общество, Wikimedia VRT ticket
  `2013112610015211`, для изданий перевода Огиенко до 1991 года;
- обязательные изменения, которые должны быть обозначены: техническая
  нормализация, токенизация, реверсификация, пословное выравнивание и
  добавление Strong;
- запрет: текст, орфография и исправления редакций УБТ после 1990 года не
  используются для замены или «улучшения» текста 1988 года;
- атрибуция не должна создавать впечатление, что УБТ, Wikimedia или
  Wikisource одобряют модуль Revelation.

Условия не расширяют выводы этапа 1: разрешение на точное издание и
производный набор не считается разрешением на позднейшие редакции УБТ.

Фактическая legacy-схема версии 3 существующих KJV/LXX_TR состоит ровно из:

- `db_metadata(key TEXT PRIMARY KEY, value TEXT NOT NULL) WITHOUT ROWID`;
- `info(code, module_id, title, description, language, canon, versification,
  license, source_summary) WITHOUT ROWID`, где все поля `TEXT NOT NULL`,
  `code` — primary key, `module_id` — unique;
- `verses(verse_key TEXT PRIMARY KEY, text TEXT NOT NULL DEFAULT '') WITHOUT
  ROWID`, с проверкой длины ключа `3`.

`lib/infra/db/bible/bible_module_db.dart` читает этот контракт при
`schemaVersion = 3`, сортирует строки по `verse_key` и исключает пустые строки
только в `readAllVerses`. Для украинского модуля пустые строки запрещены.

`scripts/content_tool/mixins/bibles.py` динамически обнаруживает
`bible_*.sqlite`, без allowlist, читает те же поля `info` и `verses`, использует
`assets/data/bible_verse_map.json` для навигации и при сохранении увеличивает
`db_metadata.data_version`. Его константа схемы равна `3`.

`scripts/bible_module/schema.py` описывает отдельную расширенную внутреннюю
схему нормализации с таблицами `bible_modules`, `canonical_verses`, `tokens`
и другими. Она пригодна как staging-модель, но **не является** прикладной
схемой распространяемого модуля и не копируется в итоговый SQLite.

Сборщики KJV и LXX_TR создают одну и ту же прикладную схему и одну
последовательность base36-ключей. LXX_TR подтверждает допустимость явных
merge/split/range-проекций и хранения явно обозначенного paratext, но его
конкретные греческие правила не переносятся на украинский текст.

### Целевая схема комментариев к стихам

Украинский `bible_ohienko_1988.sqlite` использует прикладную schema version 4.
Таблицы `db_metadata` и `info` сохраняют контракт версии 3, а таблица стихов
имеет точную форму:

```sql
CREATE TABLE verses (
  verse_key TEXT NOT NULL PRIMARY KEY CHECK(length(verse_key) = 3),
  text TEXT NOT NULL DEFAULT '',
  comment TEXT NOT NULL DEFAULT ''
) WITHOUT ROWID;
```

Для кандидата обязательны `PRAGMA user_version = 4` и
`db_metadata.schema_version = '4'`. Столбец `comment` существует в каждой из
31 102 строк: пустая строка означает отсутствие сноски, `NULL` запрещён.

В рамках этой roadmap файлы KJV/LXX_TR не переписываются и остаются на
schema version 3 без `comment`. Runtime и content tool должны поддерживать
обе версии и определять возможность комментариев по фактическим столбцам
`verses`, а не по `module_id`. Legacy-модуль без столбца читается как модуль с
пустыми комментариями; попытка записать комментарий в него не должна молча
менять его схему.

`comment` содержит только отображаемый Unicode plain text печатных сносок,
связанных со стихом. При нескольких сносках блоки записываются в исходном
порядке и разделяются двумя LF. Печатный маркер, если он есть, сохраняется в
начале соответствующего блока; отсутствующий маркер не создаётся. Полные raw
значения, anchor offsets и provenance остаются в промежуточном корпусе, чтобы
значение SQLite можно было воспроизвести. `comment` не содержит Strong-токены,
не входит в `verses.text`, библейский plain-text поиск или обычное копирование
стиха.

## Выбор целевой сетки и доказательство сохранности

### Зафиксированное решение

Целевая сетка — `kjv_protestant`. Это решение не основано на сходстве с RST.

Исходные посылки:

1. Владелец и этап 1 зафиксировали полный 66-книжный Ветхий и Новый Заветы
   юбилейного издания 1988 года без дополнительных книг.
2. Целевая сетка содержит те же 66 книг в том же каноническом порядке.
3. Различие границ стихов не требует потери текста: исходные границы
   сохраняются отдельно, а целевой результат строится только явными
   операциями `1:1`, `merge`, `split` и `range_transfer`.
4. Нумерованный канонический текст и paratext имеют разные потоки. Материал,
   не являющийся целевой стиховой строкой, остаётся в промежуточной модели с
   явным disposition и не исчезает молча.
5. Для каждой книги действует инвариант сохранности: после разрешённой
   нормализации конкатенация принятого исходного канонического plain text
   должна быть точно равна конкатенации plain text целевых строк; каждый
   исходный Unicode scalar и каждая принятая Strong-связь потребляются ровно
   один раз либо записываются как явно классифицированный paratext.

Следовательно, одинаковый канон и явная сохраняющая порядок many-to-many
проекция делают KJV-сетку технически способной представить всё каноническое
содержание издания без потери и без подмены исходной нумерации. Утверждается
**представимость**, а не ложное `1:1`-совпадение всех ссылок.

Этап 5 обязан доказать инвариант на полном закреплённом корпусе и построить
прямую и обратную карту для каждой записи. Если этапы 3–5 обнаружат
канонический материал вне 66 книг, нарушение порядка книг или невозможность
сохранить текст/Strong при этой проекции, это `critical`: этап 2 открывается
повторно, сборка блокируется и запрашивается отдельное архитектурное
согласование другой сетки. Это жёсткий gate, а не открытое решение
спецификации.

## Промежуточная модель

Единица промежуточного корпуса — JSON-объект `VerseProjectionRecord`:

| Поле | Тип и контракт |
| --- | --- |
| `record_id` | стабильная уникальная строка |
| `edition_id` | строго `ohienko_1988` |
| `source_id` / `source_revision` | ID и закреплённая версия фактического источника |
| `source_ref_raw` | ссылка ровно в представлении источника |
| `source_ref_normalized` | разобранные книга/глава/стих/subverse, без подмены target ref |
| `source_order` | целое число полного порядка внутри издания |
| `source_kind` | `canonical_text`, `psalm_superscription`, `section_heading`, `footnote`, `variant`, `colophon`, `publisher_matter` |
| `source_plain_raw` | извлечённый Unicode plain text до нормализации |
| `source_plain_nfc` | NFC-представление для сравнения; лексика и пунктуация неизменны |
| `target_refs` | упорядоченный непустой массив целевых `canonical_ref`/`verse_key` либо пустой только для paratext |
| `target_spans` | точные диапазоны Unicode scalar/token для `split`/`range_transfer` |
| `tokens` | упорядоченный массив токенов по описанному ниже контракту |
| `footnotes` | упорядоченный массив объектов с полным raw/norm-текстом, печатным маркером, anchor offsets, `source_id`, `source_order` и статусом привязки |
| `target_comment` | итоговая строка для `verses.comment`, пустая до завершённой проекции сносок |
| `text_source_ids` | источники украинского текста |
| `strong_source_ids` | источники Strong/оригинального языка |
| `transformation` | `1:1`, `merge`, `split`, `range_transfer`, `outside_grid` |
| `confidence` | число `[0,1]`, метод вычисления фиксируется версией выравнивателя |
| `decision_comment` | обязательное объяснение для любого не-`1:1` случая; не является текстом сноски |
| `disposition` | решение для paratext или `included_in_target` |

Токен содержит:

`token_id`, `kind`, `surface`, `start_scalar`, `end_scalar`,
`alignment_form`, `strong_raw`, `strong_relation`, `strong_candidates`,
`strong_final`, `strong_source_ids`, `confidence`, `alignment_comment`.

`start_scalar:end_scalar` ссылается на диапазон Unicode scalar в
`source_plain_nfc`. `strong_raw` всегда сохраняет исходное значение.
`strong_relation` принимает `single`, `simultaneous`, `alternative`,
`compound` или `none`. Финальный Strong не вычисляется потерей суффикса.

## Правила проекции

- `1:1`: одна исходная стиховая запись даёт одну целевую строку; порядок
  surface-текста не меняется.
- `merge`: несколько смежных исходных записей одной книги объединяются в
  одну цель в исходном порядке. На границе добавляется ровно один пробел,
  только если граница уже не содержит пробельный символ.
- `split`: одна исходная запись делится на смежные целевые строки по
  явно записанным scalar/token offsets. Диапазоны не пересекаются, покрывают
  весь принятый текст ровно один раз и не разрывают grapheme cluster.
- `range_transfer`: несколько смежных исходных записей отображаются на
  несколько смежных целевых строк той же книги. Для каждого целевого
  фрагмента записаны исходные диапазоны; перестановка и межкнижный перенос
  запрещены.
- `outside_grid`: разрешён только для классифицированного paratext.
  Канонический текст не может получить этот disposition.

Для каждой книги автоматически проверяются:

1. полное покрытие исходных canonical records;
2. ровно одна итоговая непустая строка на каждый baseline key;
3. отсутствие дубликатов scalar/token ranges;
4. точное равенство исходной и целевой plain-text конкатенации после NFC и
   нормализации только пробельных границ;
5. обратимость карты target → source;
6. отсутствие потери или дублирования разрешённых Strong-связей;
7. отсутствие потери, дублирования и переноса сносок к неверному
   `verse_key`.

## Заголовки, сноски и материал вне сетки

- Заголовок книги, главы и редакционный подзаголовок сохраняется как
  `section_heading`/`publisher_matter` в промежуточном JSONL, но не входит в
  `verses.text` и не получает Strong.
- Заголовок/надписание псалма и нулевой стих сохраняется как
  `psalm_superscription`, привязывается к следующему целевому стиху и
  включается перед его текстом в квадратных скобках. Исходная ссылка и
  граница сохраняются отдельно; искусственный `verse_key` не создаётся.
- Сноска сохраняется отдельно с полным raw/norm-текстом, печатным маркером,
  anchor offsets, исходным порядком и provenance, затем привязывается к
  соответствующему исходному стиху и проецируется в `verses.comment`.
- При `1:1` сноска остаётся у того же смыслового стиха. При `merge` блоки
  объединяются в исходном порядке. При `split` сноска назначается по anchor
  range; неоднозначный или отсутствующий anchor требует ручного решения и не
  разрешает автоматический перенос к ближайшему стиху.
- Маркер и текст сноски не входят в `verses.text`, runtime plain text или
  Strong-разметку. `preserved_external_footnote` допустим только для материала,
  который доказанно не относится ни к одному стиху; он требует причины, теста
  и ручного решения, а не используется как обычный способ исключить сноску из
  SQLite.
- Вариант чтения в основном печатном тексте сохраняется дословно. Вариант
  только в сноске не заменяет основной текст и хранится как `variant`.
- Квадратные, круглые и другие скобки основного текста сохраняются
  дословно. Проектные квадратные скобки paratext маркируются происхождением,
  чтобы их не спутать с печатными.
- Текстовый колофон/подписка, относящийся к библейскому тексту, сохраняется
  как `colophon` и добавляется в квадратных скобках после последнего
  связанного стиха. Издательские и типографские сведения сохраняются как
  `publisher_matter`, но не входят в SQLite.
- Дополнительная книга или канонический фрагмент вне 66-книжной сетки не
  исключается: это `critical`, повторное открытие этапов 1–2 и остановка до
  архитектурного согласования.
- Любое сознательное исключение имеет `source_id`, ссылку, полный raw text,
  disposition, причину и тест; молчаливое удаление запрещено.

## Украинская токенизация и plain text

1. `source_plain_raw` неизменяем; отдельное `source_plain_nfc` применяет
   Unicode NFC и унифицирует только окончания строк.
2. Финальная строка сохраняет украинские буквы, регистр, ударения,
   апострофы, дефисы, тире, скобки и пунктуацию точного издания. Не
   выполняются модернизация орфографии, замена слов или сверка по поздней УБТ.
3. Word token — максимальная последовательность Unicode-категорий
   `Letter`/`Mark`, допускающая внутренние апострофы `U+0027`, `U+2019`,
   `U+02BC` и дефисы `U+002D`, `U+2010`, `U+2011`, если по обе стороны есть
   буква/mark. Цифровая последовательность — `number`; остальное —
   `punctuation`.
4. `alignment_form` строится только для сопоставления: `casefold`, варианты
   апострофа приводятся к `U+02BC`, варианты внутреннего дефиса — к
   `U+2010`, combining stress может быть удалён. Surface и offsets при этом
   не меняются.
5. Пунктуация остаётся при украинском surface-тексте. В runtime-строке Strong
   следует после соответствующего surface token отдельным пробельным
   `H<number>`/`G<number>` токеном.
6. После удаления Strong-токенов штатным правилом `^[GH]\d+$`, NFC и
   схлопывания пробелов runtime plain text должен точно совпадать с
   нормализованным целевым plain text. Проверка выполняется для всех
   31 102 строк.

## Нормализация Strong

Нормативная реализация:
[`ukrainian_strong.py`](../../../scripts/bible_module/ukrainian_strong.py).

- Финальный синтаксис: `^[HG][1-9][0-9]*$`.
- Classic Hebrew: `H1`–`H8674`.
- Classic Greek: `G1`–`G5624`.
- Регистр префикса нормализуется, ведущие нули удаляются.
- В финальном ВЗ допускаются только `H...`, в финальном НЗ — только `G...`.
- Несколько одновременных classic Strong одного украинского surface token
  сохраняются в стабильном порядке и дедуплицируются только после явного
  разрешения.
- Extended/augmented Strong сохраняется дословно в `strong_raw`. Он
  переводится в classic только точным versioned mapping. Суффикс нельзя
  молча отбрасывать.
- Зафиксированные текущим контрактом замены:
  `G6031→G1650`, `G6053→G2737`, `G6063→G1492`, `G6083→G4894`,
  `G6094→G3166`.
- Alternative Strong сохраняет отношение и кандидатов. До явного выбора
  primary значение не входит в runtime.
- Composite Strong разбирается только грамматикой конкретного закреплённого
  источника; компоненты и отношение сохраняются. Разделение по знаку без
  знания семантики запрещено.
- Неизвестный extended, конфликт mappings, нулевой/вне диапазона или
  malformed Strong блокирует финальный вывод. Потеря через `None`, пустую
  строку или молчаливое отбрасывание запрещена.

## Метрики аудита

Для каждого стиха и каждого контрольного источника сохраняются:

- наличие и непустота украинского plain text;
- exact plain-text equality после разрешённой нормализации;
- количества украинских word tokens, Strong links и слов без Strong;
- multiset intersection с учётом кратности;
- `precision = |A∩B| / |A|`, `recall = |A∩B| / |B|`;
- `F1 = 2PR / (P+R)`;
- `Jaccard = Σ min(countA,countB) / Σ max(countA,countB)`;
- длина LCS Strong-последовательностей;
- `ordered_precision = LCS/|A|`, `ordered_recall = LCS/|B|`,
  `ordered_F1`;
- собственный F1 и F1 с предыдущим/следующим стихом;
- согласие базовой транскрипции с печатным эталоном и независимым контролем;
- количество сносок, exact equality их нормализованного текста, маркеров и
  порядка, статус anchors и соответствие итогового `comment` целевому стиху;
- подтверждение, что комментарий не попал в `verses.text`, Strong-набор,
  библейский plain-text поиск или обычное копирование стиха;
- применённые projection/override и их confidence.

Для пустых множеств: два пустых множества дают precision/recall/F1/Jaccard
`1`; только одно пустое — `0`. Деление на ноль не скрывается как `null`.

Триаж-сигналы Strong:

- F1 `<0.50` или Jaccard `<0.35` — `high`;
- `0.50≤F1<0.75` — `medium`;
- `0.75≤F1<0.90` — `low`;
- LCS ordered F1 `<0.45` повышает сигнал на один класс, но не выше `high`;
- если лучший сосед имеет F1 `≥0.60` и превосходит собственный минимум на
  `0.20`, сигнал `high`;
- если сосед имеет F1 `≥0.50` и превосходит собственный минимум на `0.10`,
  сигнал минимум `medium`;
- ноль финальных Strong при непустом контрольном множестве — `high`;
- доля unresolved/missing Strong `>20%` — `high`, `(5%,20%]` — `medium`,
  `(0%,5%]` — `low`.

Низкая метрика — сигнал проверки, а не автоматическое доказательство ошибки
перевода. Решение основывается на украинском контексте, оригинале,
версификации и источниках.

## Классы аномалий

### `critical`

- неверный SHA/schema/metadata/ID или `integrity_check`;
- отсутствующий, лишний, повторный или переставленный baseline key;
- пустая целевая строка;
- потеря/дублирование канонического Unicode-текста;
- попадание текста поздней редакции УБТ;
- канонический материал вне утверждённой сетки;
- неразрешённый межкнижный/межзаветный перенос;
- недействительная лицензия/атрибуция;
- invalid/out-of-range Strong или молчаливая потеря extended/composite данных;
- потеря, дублирование или попадание сноски в канонический `verses.text`.

### `high`

- неразрешённое не-`1:1` правило;
- лексическое расхождение точного украинского текста с печатным эталоном;
- unresolved extended/alternative Strong;
- Strong без украинского слова или связь с явно неверным стихом;
- сильный соседний сдвиг или высокий Strong-триаж-сигнал;
- сноска, привязанная к неверному стиху, или неразрешённая неоднозначность
  anchor при `split`/`range_transfer`;
- paratext без disposition;
- конфликт независимых источников, влияющий на текст или разметку.

### `medium`

- умеренный Strong-триаж-сигнал;
- токенизационная неоднозначность апострофа/дефиса/составного выражения;
- частичное отсутствие Strong при объяснимом переводческом расхождении;
- пунктуационное или вариантное расхождение, требующее ручного решения.

### `low`

- только пробельное/типографское различие;
- ожидаемое лингвистическое расхождение при корректной ссылке;
- документированное отсутствие Strong у служебного украинского слова;
- редакционный paratext с однозначным disposition.

Этапы 6 и 8 не закрываются при любом нерешённом `critical/high`. `medium/low`
должны иметь решение или явную приёмку владельца по правилам roadmap.

## Форматы и расположение отчётов

Корень каждого этапа:

`scripts/bible_module/reports/ukrainian_stage_<stage>_<YYYYMMDD>/`.

Форматы:

- JSON: UTF-8, LF, `schema_version`, стабильный порядок записей, числа как
  числа, отсутствие `NaN`/`Infinity`;
- JSONL: один объект на строку UTF-8/LF, сортировка по `source_order`, затем
  `record_id`;
- CSV: UTF-8, comma delimiter, обязательный header, quoting по RFC 4180,
  стабильная сортировка по target order;
- Markdown: русскоязычное резюме с командами, SHA-256, counts, ограничениями
  и ссылками на JSON/CSV.

Нормативные имена будущих артефактов:

- этап 3: `source_lock.json`, `fetch_log.json`, `source_files.csv`;
- этап 4: `normalized_<source_id>.jsonl`, `source_stats.json`,
  `source_diff.csv`, `report.ru.md`;
- этап 5: `versification_map.jsonl`, `projection_rules.json`,
  `coverage.json`, `anomalies.jsonl`, `manual_review.md`;
- этап 6: `aligned_corpus.jsonl`, `strong_overrides.jsonl`,
  `comment_overrides.jsonl`, `strong_stats.json`, `footnote_stats.json`,
  `strong_diff.csv`;
- этапы 7–8: `build_stats.json`, `audit_summary.json`,
  `verse_metrics.csv`, `anomalies.jsonl`, `report.ru.md`;
- этапы 9–12: `validation_log.md` и предусмотренные roadmap отчёты.

Полные защищённые исходники не добавляются в Git без отдельной проверки
права и необходимости. Отчёты не должны случайно дублировать полный текст.
