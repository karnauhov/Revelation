# Общая панель локальных сборок

Doc-Version: 1.3.1
Last-Updated: 2026-11-01
Source-Commit: working-tree

Постоянный адрес на компьютере владельца: **http://127.0.0.1:8877**.
Сервис слушает только loopback, читает один реестр и существующие каталоги. Показывает
версии/build/SHA, платформы, checkpoints, ошибки и журналы без копирования пакетов.
Скачивание проверяет SHA-256 manifest. Непроверенные пакеты отличаются от принятых.
Длинные имена этапов переносятся внутри карточки, а время и статус занимают отдельные места.
На узком экране карточки ОС располагаются последовательно. Ошибка текущего этапа показывается
вместо общего сообщения оболочки pipeline; подробная история остаётся в журнале.
Исторические выпуски доступны для скачивания без кнопок сборки.
Завершённая ОС показывается отдельно от готовности всего выпуска. Над карточками перечислены
конкретные оставшиеся обязательные проверки и показано количество пакетов из ожидаемого комплекта.
После подтверждённой публикации статус меняется на «Опубликовано», появляется ссылка GitHub,
а кнопки повторной сборки скрываются. Локальные ссылки продолжают вести к единственным файлам каталога.
Новые подготовленные задания и архив сортируются вместе по числам версии/build: 1.0.10 идёт после 1.0.9,
build1000 после999. Задание появляется сразу после подготовки, до первого пакета или manifest.
Если текущая ОС завершила обязательные проверки, а другая ещё ожидается, статус - «Ожидание другой ОС».
Панель указывает нужную ОС и сохраняет готовые пакеты до следующего входа на соответствующий builder.
Время измеренных этапов видно сразу в каждой карточке ОС, текущий этап обновляется во время работы.
Новые замеры используют monotonic clock, включают повторные попытки и сохраняются при invalidation checkpoints.
Вложенные integration-файлы не прибавляются повторно к родительскому этапу. Ожидание другой ОС не входит в сумму.
Для старых результатов показана оценка по started/finished; знак ≥ означает недоступные старые замеры,
в том числе обратный перевод системных часов. Это время самих этапов, а не промежуток между перезагрузками.
Ранее подготовленные задания сохраняют закреплённый runtime и старые отметки времени. Точные монотонные замеры появляются в новых заданиях либо после проверенного обновления runtime существующего задания.

## Windows

Общий реестр: `%LOCALAPPDATA%/AI11/LocalRelease/registry.json`.
Revelation использует канонический `.local-releases` и личный `.local-releases/windows-config.json`.
Этот конфиг никогда не выдаётся через HTTP. Установка/восстановление из main:

```powershell
python scripts/local_release/release.py register-project --repo . --profile scripts/local_release/revelation.json --root .local-releases --config .local-releases/windows-config.json
python scripts/local_release/release.py install-service
```

Пользовательский Startup shortcut `AI11 Local Builds.lnk` запускает `pythonw.exe` после входа,
без терминала и прав администратора. Установка перечитывает target/arguments и сохраняет
их в `startup.json` рядом с реестром. Чужой одноимённый shortcut не перезаписывается.
Git проверяется каждые 30 секунд; после включения trigger Git hook передаёт новые коммиты сразу.
Draft-результаты Linux принимаются каждые 5 минут в покое и каждую минуту при сборке.
UI обновляется каждые 10 секунд в покое и каждые 3 секунды при сборке; в скрытой вкладке опрос приостановлен.
Финализация GitHub Release требует всех gates; незавершённый выпуск остаётся private.
Автобилд Windows включён после полного опубликованного пробного выпуска REV301/build173.
Новый обычный коммит получает следующий build и собственную строку очереди; готовый173 не пересобирается.

После обновления main перезапустите сервис:

```powershell
python scripts/local_release/release.py stop-service
python scripts/local_release/release.py start-service
```

Остановка кооперативная: дождитесь завершения процесса из `service.json` и ответа HTTP
перед запуском обновлённого кода. `start-service` повторно использует живой экземпляр.
Для удаления автозапуска остановите сервис и удалите только его отмеченный shortcut из
пользовательской папки Startup. Реестр, настройки, журналы и пакеты сохраняются.
Занятый порт даёт ошибку в private `service.log`; чужой процесс не завершается и порт не меняется.

## Linux

Однократный запуск из checkout:

```bash
git fetch origin
git switch main
git pull --ff-only
bash scripts/local_release/run-linux.sh
```

Он устанавливает `~/.config/autostart/ai11-local-builds.desktop`, реестр и version hook,
поднимает ту же панель и запускает последовательный dispatcher. Следующие графические входы
открывают собственный терминал прогресса, обновляют main, принимают runtime repairs и строят
зарегистрированные Linux-проекты. После отчёта владелец вручную возвращается в Windows.
Удаление Desktop Entry отключает Linux autostart. Общего диска между ОС не требуется.
Автоматический повторный Ubuntu login, получение задания, полный Linux trial и возврат результатов проверены владельцем.

## Управление

`Запустить` и `Повторить` продолжают checkpoints, сохраняя успешные этапы с проверенными выходами.
`Перезапустить` сначала просит остановку и ждёт освобождения builder. `Остановить` относится только
к выбранному заданию: координатор завершает его дочерний процесс, восстанавливает integration fixtures
и передаёт диагностику. Сетевые запросы могут задержать остановку. OS lock после рестарта сервиса
отличает живую сборку от прерванной. Другая недоступная ОС показывается ожиданием.

POST требует токен текущей панели и допустимые Host/Origin, CORS отсутствует.
HTTP выдаёт только manifest-пакеты и redacted tail журналов до 512 КиБ. Конфиги, keystore,
credentials и произвольные пути недоступны; данные UI выводятся текстом.

## Удаление сборки

GitHub Release определяется по фактическому tag из job/manifest и проверенному source SHA,
включая auto-теги. Старые ошибочные записи «GitHub удалено» перепроверяются по уникальному
маркеру project/SHA без изменения подтверждённого запроса. Завершение требует реального
отсутствия Release и обоих управляемых Windows-каталогов.

Windows builders передают Gradle `-Dorg.gradle.daemon=false`, чтобы JVM не удерживала lint JAR
после сборки. Для старого дерева Restart Manager определяет владельца блокировки. Останавливать
можно только IDLE Gradle daemon, удерживающий JAR этого каталога: PID и время создания
проверяются, IDLE повторно проверяется перед остановкой. Активные и посторонние процессы
сохраняются; удаление остаётся незавершённым для повтора.

Кнопка `Удалить` сначала открывает обязательный диалог с версией, build, полным SHA, числом пакетов и областью удаления.
`Отмена` и Escape ничего не удаляют. Подтверждение действует пять минут и относится только к выбранному project/SHA.
Активный builder останавливается, пользовательские данные приёмки восстанавливаются. Удаляются точный локальный
каталог/checkout и matching GitHub Release; исходный код main, Git-тег и установленное приложение сохраняются.

Небольшая метка удаления сначала записывается с проверкой read-back в `refs/notes/ai11-local-retention` этого репозитория.
Это Git notes, без новой ветки и без записи в историю main. Управляющие коммиты содержат реальный код задачи и `[skip ci]`.
Ошибка сети сохраняет пакеты и позволяет повторить тот же запрос. Linux получает notes автоматически до jobs,
запрещает восстановление удалённого SHA и при необходимости убирает незавершённую попытку. Постоянного архива у него нет,
поэтому Windows/GitHub deletion не ждёт Linux login/ack. Панель показывает завершение после очистки постоянных каталогов.
Старый control draft автоматически переносится в notes и удаляется после проверки; новый retention draft не создаётся.

## Другие проекты

В соответствующей задаче проекта создайте профиль общего движка, helper версий, gates и свой
gitignored каталог. Зарегистрируйте их через `register-project` без второго сервиса/копий пакетов.
Для Linux добавьте явную запись в `scripts/local_release/projects.json`: project, repository,
directory, profile, hosts, enabled. Произвольные папки не сканируются. Личные credentials каждой ОС
остаются у неё. Автобилды других проектов реализуются в их собственных задачах.

[Протокол обмена между ОС](protocol.ru.md) · [Выпуск и gates](local-release.ru.md).

Windows очищает проверенный managed-каталог через extended-length paths, включая длинные Gradle-файлы
и readonly Git-файлы. Частичный отказ не создаёт OS ack: локальная очистка должна физически завершиться.
Повтор продолжает исходный request; уже удалённый GitHub Release повторно не удаляется.
Подтверждённая версия сразу исключается из обычной очереди, чтобы не восстановиться автоматически.
До завершения очистки раздел «Удаление сборок» явно показывает «осталось удалить» или ошибку;
длинный путь переносится внутри боковой панели.

## Подсказки и диагностика Linux

Управляющие кнопки показывают описание при наведении и клавиатурном фокусе; Escape закрывает подсказку.
Текст учитывает ОС, активный процесс и завершённые проверки. «Перезапустить» останавливает процесс и продолжает по checkpoints,
а не требует полной пересборки. После завершения Windows запуск/повтор дополнительно передаёт Linux запрос продолжения на следующий вход.
Неактивная «Остановить» тоже записывает и отправляет журнал. Диалог удаления сохраняет отдельное подтверждение.

Блок «Последний отчёт Linux» показывает время получения, последний этап, доступные замеры, ошибку и хвост журнала.
Это отдельная диагностика, она не подменяет quality gates. Если отчёт не был передан, панель прямо сообщает об отсутствии данных.
Прогресс отправляется раз в минуту во время Linux-сборки; завершение, ранняя ошибка и результат очистки отправляются отдельно.
Windows сохраняет полученную историю в `.local-releases/host-reports/`; все полные журналы задания остаются в каноническом каталоге версии.
В Linux постоянного архива нет - см. [политику временного сборщика](local-release.ru.md#linux---временный-сборщик).

Управление не показывает одинаковые действия одновременно: новая сборка имеет «Запустить», попытка с историей - «Повторить»; «Перезапустить» доступна только активному процессу. У завершённой текущей ОС скрыта бессмысленная остановка. История последних отчётов Linux открывается отдельными ссылками на сохранённую Windows-копию.

Автозапуск Windows вызывает идемпотентный `start-service`: он переиспользует живой сервер или скрыто запускает его с `service.log`.
Короткие конкурентные записи очереди ожидают до пяти секунд, не перехватывая чужую блокировку.
Реальный Ubuntu runtime4/build174 прошёл Snap acceptance, verified delivery и cleanup; Windows принял результат автоматически.
