## Доступность номеров Стронга в модуле

`BibleModuleDB.readInfo` определяет `BibleModuleInfo.hasStrongNumbers` по отдельным токенам G/H с цифрами в тексте всех стихов. SQL отбирает кандидатов ограниченными пакетами, проверка использует общий с чтением контракт токена; сноски не учитываются. Признак входит в сравнение значения и обновляется при чтении сведений о модуле без изменения SQLite-схемы или постоянного кеша. Каждая панель выводит доступность кнопки и пункта меню Стронга из своего `selectedModule`; дополнительного флага видимости в состоянии нет. Выбор показа номеров сохраняется при переходе через текстовый модуль, а самостоятельный словарь остаётся доступным.

## Метаданные ревизии модуля Библии

DB-адаптер читает необязательные метаданные ревизии из того же файла, что и сведения о модуле. `BibleModuleInfo` хранит nullable-версии/дату со сравнением по значению; выбранный модуль остаётся в ведении репозитория и ReaderCubit. Только presentation преобразует известные значения языка/набора книг/нумерации в понятные локализованные названия, форматирует календарную дату ревизии без сдвига часового пояса устройства и сохраняет неизвестные значения и полные сведения об источнике/лицензии. Код и ID модуля остаются внутренними данными и не показываются в информационном диалоге. Схемы и содержимое БД не меняются.

## Параллельное чтение по умолчанию и по ссылке

`BibleWorkspaceCubit` открывает новый workspace с LXX/TR и доступным переводом на языке приложения; соответствие языка проверяется по метаданным опубликованных модулей. Сейчас доступны KJV (en) и OH1988 (uk); при отсутствии перевода es/ru или ошибке чтения его метаданных остаётся исходный модуль. Дополнительные модули не выдумываются. Явный `module` в ссылке имеет приоритет; недоступный модуль возвращает штатный оригинал/первый доступный модуль, а не сохранённый выбор.

Обычный `/bible` восстанавливает сохранённый набор панелей (включая legacy-выбор одного модуля). `bible:` и `/bible` с параметрами ссылки открывают исходную книгу/главу/стих и перевод независимо от сохранённой раскладки; формат существующих маршрутов сохранён. Автоматическое открытие и навигация не записывают настройки. Только явное добавление/закрытие панели или успешная смена модуля сохраняют полный готовый набор. Workspace — единственный владелец записи; ReaderCubit больше не записывает общий single-module preference. Записи выполняются последовательно, незагруженные панели не сохраняются. Начальная загрузка объединяется, закрытие и ручное изменение раскладки отменяют применение запоздалого автоматического подбора. Режим связанной навигации по-прежнему относится к текущему workspace. Подбор перевода выполняется один раз; после медленной загрузки новая панель получает актуальную ссылку основной, дожидаясь текущей синхронизации.

## Повтор первого открытия Библии

`BibleReaderCubit.retryInitialLoad` повторяет только неудачную начальную загрузку, сохраняя исходные параметры маршрута. Доступность кнопки выводится из failure и отсутствия verseMap; повторный запрос синхронно переводит Cubit в loading, поэтому быстрые нажатия объединяются. Существующий LatestRequestGuard защищает от устаревших ответов и завершения после close. Workspace, репозиторий и схема состояния остаются единственными владельцами своих данных; отдельное состояние повтора не вводится.

## Текстовые модули Библии и сноски

BibleModuleDB отвечает за определение возможностей схемы и возвращает пустой comment для legacy-файлов. BibleVerseText и BibleChapterVerse хранят text и comment как отдельные сравнимые значения. BibleRepository передаёт комментарий в данные главы, исключая его из текстового поиска. BibleVerseCommentButton отвечает за локализованное представление диалога без параллельного среза состояния. Python-редактор сохраняет текст/комментарий атомарно и динамически обнаруживает столбец. Существующее сравнение содержимого таблиц учитывает изменения comment; различия только метаданных по-прежнему исключены из сводок содержимого.

## Strong Feature Notes

- Асинхронное состояние подсказок ссылок на стихи принадлежит `strongs_dictionary/presentation/bloc/StrongUsagePreviewCubit`; локализация и показ Tooltip остаются в виджете.
- `features/strongs_dictionary` владеет domain/data/presentation-логикой словаря Стронга, включая page/dialog/picker/embedded-потоки.
- `shared/ui/markdown` остаётся независимым от Strong и не должен содержать Strong-специфичные маркеры или inline-обработчики синтаксиса.

## Назначение

Определить, где должен лежать код и как направлены зависимости между слоями.

## Верхний уровень

- `lib/app` - bootstrap, startup shell, DI, router, верхнеуровневая сборка приложения
- `lib/core` - кросс-функциональные примитивы: ошибки, async guards, logging, audio, platform utilities, diagnostics
- `lib/infra` - реализации доступа к БД, remote и storage
- `lib/shared` - переиспользуемый UI, общие модели, localization helpers и общие утилиты
- `lib/features` - feature-first модули
- `lib/l10n` - ARB-файлы и generated localization-код

## Структура feature-модуля

Если feature нужен внутренний слойный разрез, используется схема:

- `presentation` - `bloc/`, `screens/`, `widgets/`
- `application` - orchestration и use-case сервисы
- `data` - repositories, data models и mapping

Feature может быть легче и не содержать все слои, но направление зависимостей не меняется.

## Правила зависимостей

- `presentation` может зависеть от feature-сервисов, репозиториев и DI-фабрик, но не от низкоуровневых infra manager-классов напрямую.
- `app/startup` может зависеть от app bootstrap/composition-кода и shared localization/theme-примитивов, но не должен переносить feature-специфичное владение state в корневой shell.
- В `presentation/bloc` и `application` не передаётся `BuildContext`.
- `application` не содержит виджеты.
- `data` может использовать infra gateways и storage-реализации.
- `infra` не импортирует feature presentation-код.
- `shared` остаётся переиспользуемым и не хранит feature-специфичную orchestration-логику.
- `core` остаётся feature-agnostic.
- Глобальная markdown image policy разделена по слоям: контракты load/request живут в `core/content/markdown_images`, дефолтная downloader/cache-имплементация живёт в `infra/content/markdown_images`, а per-document UI-state и render-логика живут в `shared/ui/markdown`.
- Feature-модули не владеют markdown image caching и preload policy; они только передают markdown-контент и feature-specific link handlers в общие markdown-виджеты.
- `features/strongs_dictionary` владеет domain/data/presentation-логикой словаря Стронга, включая picker/dialog/page-потоки и встроенный UI словарной статьи для первоисточников.
- `shared/ui/markdown` должен оставаться независимым от Strong: без Strong-специфичных маркеров, syntax handlers или feature tooltip renderers.
- `features/bible` владеет поиском модулей Библии, локальными настройками модулей, состоянием чтения каждой панели и экраном чтения Библии; общий обработчик ссылок может направлять `bible:`-ссылки в этот feature, но не владеет состоянием чтения.

## Правила состояния

- Stateful presentation строится только на `Cubit`/`Bloc`.
- Для каждого UI-среза данных есть один source of truth.
- Не добавляются дублирующие cubit-ы и visibility-флаги, если состояние выводится из уже существующих данных.
- Async cubit-ы после `await` защищают применение state через `isClosed` и stale-request protection там, где возможна гонка.
