## Параллельное чтение и сохранение выбора

`integration_test/smoke/bible_parallel_reading_smoke_test.dart` локально проверяет en/uk: две панели по умолчанию, читаемые тексты, закрытие перевода через toolbar/меню, повторное открытие одной сохранённой панели, переход `bible:Мт17:5` и явный `module` вопреки сохранённому набору. Ссылки не перезаписывают предпочтения. Используются синтетические тексты, настоящий роутинг/экран и адаптер SharedPreferences с изолированным тестовым хранилищем; production и пользовательские данные не меняются. Запуск: `flutter test integration_test/smoke/bible_parallel_reading_smoke_test.dart -d windows`; Web — через локальный ChromeDriver и `flutter drive --release --driver=test_driver/integration_test.dart --target=integration_test/smoke/bible_parallel_reading_smoke_test.dart -d web-server --browser-name=chrome --headless --driver-port=4444 --web-port=8768`. Это целевая проверка REV127, полная приёмка версии остаётся REV236.

Widget-тесты проходят тот же пользовательский сценарий при 420×900 и 1280×800, включая переполнение toolbar. Unit-тесты покрывают en/uk и отсутствие es/ru, сохранённый выбор, приоритет ссылок, одновременные начальные запросы, закрытие во время ожидания, ручное изменение до завершения автоподбора, устаревшую смену модуля и последовательность быстрых записей.

## Первый запуск и восстановление чтения

`integration_test/first_reading_test.dart` проходит настоящий выбор языка en/es/uk/ru и сохранение настроек, ошибку первой загрузки модуля, повтор на том же экране, открытие установленной копии без сети и замену данными новой версии. Native-прогон использует временные Documents, синтетическую SQLite и loopback HTTP, не рабочие данные или production Supabase. Запускать последовательно на локальных native-устройствах: `flutter test integration_test/first_reading_test.dart -d <device-id>`. Web-пропуск этого набора не считается успешной проверкой. Отдельный `integration_test/smoke/bible_first_load_retry_smoke_test.dart` запускается в Chrome через локальный `flutter drive --release` и ChromeDriver: контролируемый отказ поиска модулей, затем настоящий Web-коннектор открывает LXX/TR из локального web/db. Это проверка UI и реального чтения, а не моделирование отключения сети браузера.

Unit-регрессии проверяют быстрые повторы, исходную ссылку, stale response и close-before-complete; widget-регрессии — локализованную кнопку и восстановленный стих на четырёх языках. Полный bootstrap остаётся в startup smoke; полная приёмка версии — REV236. [Единый актуальный отчёт REV210](rev210-first-reading.ru.md) разделяет лабораторный результат, доступность модулей и ограничения действующей аналитики.

## Текстовые модули Библии и сноски

Покрытие текстового выпуска OH1988 проверяет digest закреплённых входов, полную обратную сверку text/comment, детерминированную сборку SQLite, безопасность отказа замены и привязку сносок. Tk-тесты редактора покрывают отдельное редактирование/фильтр, откат транзакции, увеличение метаданных и legacy-совместимость. Flutter DB/model/repository/widget-тесты проверяют схемы 3/4 без смены версий, сравнение и передачу comment, исключение из поиска/копирования и клавиатурную доступность сносок. Локальный Bible navigation smoke покрывает выбор OH1988, открытие/закрытие сноски, отсутствие пустого действия и прежнюю греческую Strong-навигацию. Полная приёмка версии остаётся REV236; публикация — REV237.

## Ошибки открытия локальной папки

`LocalFolderOpenException` сохраняет определённый путь папки приложения, исходную причину и стек при ошибке создания или открытия папки. Если определить путь не удалось, экран «О программе» сохраняет общее локализованное сообщение. Unit-тесты покрывают исключения процесса, отказ desktop/mobile launcher, ошибку создания и неопределённый путь; widget-тесты и контракты локализации проверяют точный путь с пробелами и Unicode на четырёх языках.

Выполняйте локально `flutter test integration_test/about_local_folder_test.dart -d windows`: проверка проходит реальное действие раздела «Инструменты» экрана «О программе», создание временной папки и намеренный отказ на границе launcher для en/es/uk/ru. Файловый менеджер не открывается, рабочие БД не меняются. На Web проверка явно пропускается как native-only и не считается успешной. На других native-устройствах доступен тот же набор; записывайте только фактически проверенные устройства.

## Слои тестов

- Unit-тесты лежат в `test/` и покрывают cubit-ы, сервисы, репозитории, router-контракты и shared helper-ы.
- Widget-тесты проверяют поведение экранов и виджетов. При необходимости слой можно запускать отдельно через теги.
- Smoke integration-тесты лежат в `integration_test/smoke/`.
- Общие test helper-ы описаны в [`test/test_harness/README.md`](../../../test/test_harness/README.md).

## Системные панели Android и оптимизация выпуска

При запуске Android явно включается `SystemUiMode.edgeToEdge` до отрисовки. Unit-тесты проверяют порядок вызовов и отсутствие изменений на других платформах. Widget-тесты заставки покрывают системные панели в портретном режиме и вырезы в альбомном. Локальный `integration_test/smoke/app_startup_smoke_test.dart` проверяет заставку, меню и drawer относительно реальных системных отступов; на Android дополнительно требует ненулевой отступ строки состояния и проверяет поворот в альбомный режим. Запускать локально: `flutter test integration_test/smoke/app_startup_smoke_test.dart -d <android-device-id>`. Эта нативная команда работает в Debug и не принимает `--release`. Отдельно собрать и установить release APK, затем проверить запуск, drawer и переход к чтению: R8 не оптимизирует debug-сборки. Flutter-сборки и тесты выполнять последовательно, поскольку они используют общие генерируемые регистраторы плагинов.

CI и локальные проверки используют Flutter 3.47.2 с поддерживаемым им Android toolchain: AGP 9.1.0, Gradle 9.3.1, Kotlin Gradle Plugin 2.4.0 и Java 17. AGP 9 включает оптимизированное удаление ресурсов по умолчанию; Flutter включает release-минификацию, удаление ресурсов и оптимизированные стандартные правила ProGuard. Сохранять consumer rules Flutter/плагинов, включая правила для reflection. Kotlin использует `compilerOptions` вместо удалённого DSL `kotlinOptions`. Сохранять `android.builtInKotlin=false` для немигрированных плагинов и `android.newDsl=false` для совместимости Flutter со старым DSL; это временные поддерживаемые переходные механизмы. Источники: [рекомендации Android по R8](https://developer.android.com/topic/performance/app-optimization/enable-app-optimization) и [миграция Kotlin во Flutter](https://docs.flutter.dev/release/breaking-changes/migrate-to-built-in-kotlin).

Рекомендации Play Console относятся к загруженному артефакту, сейчас 1.0.7+172. Устаревшие вызовы цветов системных панелей могут оставаться во Flutter/AndroidX для старых Android; отсутствие собственных вызовов приложения не доказывает исчезновение предупреждения. Не изменять кэш SDK и не отключать код совместимости ради сканера. Повторно проверить рекомендации после загрузки отдельно принятого выпуска в REV237; успешная локальная сборка не является публикацией или новым измерением Play.

Стабильный Android WebView 1.1.3 всё ещё запрашивает стандартный файл ProGuard, удалённый в AGP 9. [Совместимая копия с сохранённой лицензией](../../../third_party/flutter_inappwebview_android/README.md) заменяет только этот файл в обоих типах сборки. Startup smoke также загружает локальный HTML и выполняет JavaScript через настоящий Android WebView без внешних запросов. Для release-проверки собрать APK с target `integration_test/webview_release_probe.dart` и проверить видимый маркер `REV142 WebView release OK`; затем пересобрать обычный target `lib/main.dart` перед проверкой нормального запуска и перехода к чтению. Probe нельзя загружать как артефакт выпуска.

## Браузерная проверка открытия БД

`integration_test/web_database_open_test.dart` проверяет 45 конкурентных запросов к Drift worker, ожидание общей блокировки, её освобождение после ошибки и открытие/повторное открытие общих и локализованных БД из `web/db/`. Очередь и Web Lock в коннекторе предотвращают пересечение проверок OPFS, описанное в [Drift #3856](https://github.com/simolus3/drift/issues/3856).

Запустить совместимый с локальным Chrome ChromeDriver на порту 4444, затем выполнить локально:

```bash
flutter drive --release --driver=test_driver/integration_test.dart --target=integration_test/web_database_open_test.dart -d web-server --browser-name=chrome --headless --driver-port=4444 --web-port=8766
```

Используется отдельный локальный origin; данные опубликованного сайта не затрагиваются. На нативных устройствах эта браузерная проверка явно пропускается и не считается пройденной. Обновлённые вкладки одного origin используют общий Web Lock; без Web Locks очередь действует внутри одной вкладки. Старые открытые вкладки не участвуют в новой блокировке до обновления страницы.

Регрессия первого долгого нажатия на ссылку стиха в словаре проверяется в `integration_test/strong_usage_preview_test.dart`. Для Chrome заменить `--target` в команде выше на этот файл; для Windows выполнить `flutter test integration_test/strong_usage_preview_test.dart -d windows`. Проверяются одновременно видимая подсказка и однократное копирование текста.

## Проверка обновления локального модуля Библии

Нативный коннектор сравнивает `schema_version` и `data_version` самой SQLite-БД с манифестом, даже при одинаковом размере файлов. До замены проверяются целостность, размер и все метаданные объявленного выпуска; более новая локальная версия сохраняется. Неудачная загрузка не считается обновлением, а оставшаяся старая версия не считается актуальной. Манифест представляет ожидаемый выпуск, а не доказательство установки.

`test/infra/db/connectors/local_database_sync_native_test.dart` покрывает изменения данных/схемы одинакового размера, повторное открытие без повторной загрузки, отклонение устаревшего объекта, ошибки сети, повреждение и отсутствие метаданных. Общая очередь сериализует поиск модулей и обновление локальных БД; регрессия трёх параллельных читателей проверяет одну загрузку без пересечения временных файлов. Widget-тест `AboutScreen` проверяет сообщение об оставшейся старой версии.

`integration_test/bible_module_update_test.dart` проходит настоящий путь локального HTTP-хранилища, скачивания, SQLite-коннектора, репозитория и экрана чтения. Он проверяет видимую замену текста, установленную версию, отсутствие повторной загрузки и сохранение рабочей копии при рассогласовании манифеста и объекта. Все файлы синтетические и находятся во временной папке; рабочие БД и Supabase не затрагиваются.

```bash
flutter test integration_test/bible_module_update_test.dart -d windows
```

На Web этот нативный сценарий явно пропускается и не считается пройденным. Web использует отдельный коннектор и токен манифеста для сброса хранилища при следующем запуске страницы; `web_db_version_sync_plan_test.dart` проверяет смену и сохранение токена. Приёмка всей версии остаётся отдельным полным локальным прогоном.

## Автоматизация

- `.github/workflows/flutter_build.yml` повторяет форматирование, анализ, тесты, фильтрацию coverage и проверки forbidden patterns.
- Все интеграционные тесты, включая smoke, запускаются локально. Выделенный GitHub Actions workflow удалён и отключён; не создавать и не запускать его повторно, в том числе как замену недоступному локальному устройству.

## Приёмка каждой версии

- Составить сценарии только для нового и изменённого функционала версии и непосредственно затронутых взаимодействий. Полная повторная ручная приёмка всего приложения не требуется.
- Добавить или обновить интеграционные тесты для нового и изменённого функционала, страниц, окон и диалогов в том же наборе изменений. Критические стартовые и навигационные сценарии сохранять в `integration_test/smoke/`.
- Перед приёмкой и публикацией выполнить все интеграционные тесты локально, например `flutter test integration_test -d <device-id>`, на применимых поддерживаемых устройствах. Отсутствие устройства или среды записать как ограничение, а не успешную проверку; GitHub Actions для этого не использовать.
- Для ручного сценария указать понятные предусловия, шаги, ожидаемый и фактический результат, сборку, платформу, язык и доказательства. Codex выполняет доступные проверки самостоятельно; участие владельца нужно для предметных решений и недоступных ему действий.
- Поддерживать один актуальный чеклист и один полный актуальный отчёт приёмки версии. После исправления повторять затронутые сценарии и сохранять существенные доказательства.
- Публикация и развёртывание оформляются отдельной задачей версии после приёмки; результат проверяется на фактически опубликованных сборках и данных.

## Правила качества

- Новое поведение и исправления ошибок должны приходить с ближайшим релевантным unit- или widget-тестом.
- Тесты должны использовать deterministic fake/stub зависимости и не зависеть от внешней сети.
- Для high-risk state-потоков нужны сценарии на:
  - stale async race (`latest request wins`)
  - lifecycle safety (`close before async completes`)
  - rapid switching в image-preview потоках primary source
