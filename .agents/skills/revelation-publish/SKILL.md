# Публикация Revelation

Прочитай [AGENTS.md](../../../AGENTS.md), [DEV_INFO.md](../../../DEV_INFO.md) и живую задачу публикации через `revelation-task` и `ai11-task-manager`. Если владелец говорит «опубликуй новую версию», определи версию по принятому кандидату и актуальной задаче публикации. Продолжай существующую отправку этого выпуска по её ID. Уточняй у владельца, если выбранный выпуск нельзя определить однозначно или нужен вход. Веди один чеклист с текущим состоянием каждого канала. После значимых шагов перечитывай запись и сообщай прогресс в чат.

## Подготовка выпуска

1. Через [revelation-release](../revelation-release/SKILL.md) проверь приёмку, локальные интеграционные прогоны, версию, build, Git SHA, манифест, SHA-256 и подписи. Бери файлы из `.local-releases/releases/revelation/<version>+<build>/<SHA>/packages/`. GitHub Releases служит проверенным зеркалом. Сверь тег и содержимое зеркала с локальным каталогом. Для недостающего пакета продолжи соответствующий этап координатора. Сохраняй зафиксированные версию и SHA готовых пакетов.
2. Сверь [CHANGELOG.md](../../../CHANGELOG.md) и описание GitHub Release с исходным SHA принятой сборки. После сборки весь текст списка изменений зафиксирован. Менять можно только строку заголовка текущей версии: замени `In development` фактической датой в формате соседних записей и сделай номер версии ссылкой на точный тег. Убедись, что остальные строки совпадают с исходным SHA. Сделай новый действующий стабильный выпуск `Latest` и проверь публичный заголовок со ссылкой и датой, метку `Latest` и адрес `releases/latest`. Исходный тег, SHA и файлы релиза сохраняются. Короткое «Что нового» для каждой активной локали карточки подготовь по зафиксированному списку. Учитывай особенности платформ и отличай язык интерфейса от доступных переводов Библии.
3. Для изменённых данных сверяй рабочие БД, `web/db`, объект и манифест Supabase с выбранной сборкой. Используй штатную публикацию контента. Сначала загрузи изменившиеся объекты и проверь их хеши, затем обнови манифест и перечитай его с публичного адреса. Сохраняй записи более новых или отдельных уже выпущенных модулей. Проверяй фактическую загрузку нужной версии данных чистым клиентом.
4. Сверь опубликованные карточки каждого магазина с принятым интерфейсом. Для новых экранов и существенно изменившихся существующих экранов сделай реальные скриншоты приложения для нужных платформ, типоразмеров и локалей. Проверь читаемость и отсутствие личных данных, приспособь только кадрирование и формат. Добавь новые и замени устаревшие снимки, сохрани актуальные изображения остальных сценариев. Проверь порядок и предпросмотр карточки до отправки. Используй отдельную именованную браузерную сессию чата.

## Публикация

- **Web.** Разверни проверенный Web ZIP в корне `main` отдельного [Revelation.website](https://github.com/karnauhov/Revelation.website). Сохрани существующие `CNAME`, служебные файлы и контент сайта вне сборки, включая `demo/`. Проверь deployment, затем production `version.json`, фактический запуск, холодный переход в новый сценарий, правовые ссылки и `db/manifest.json` с хешем изменённого файла. Для Web сверяй одновременно версии клиента и данных.
- **Google Play.** Открой `ai11.link.revelation` в [Production](https://play.google.com/console/u/1/developers/8693299089478158768/app/4975644827990074725/tracks/production). Сверь versionCode, требование target API и действующую подпись, используй готовый AAB. Заполни примечания в тегах локалей консоли и обнови основной и применимые дополнительные листинги. Отправь изменения на проверку и отследи, требуется ли ручное завершение Managed Publishing или rollout. Сверь публичную карточку и обновление приложения после выпуска. [Релиз и rollout](https://support.google.com/googleplay/android-developer/answer/9859348), [требования к скриншотам](https://support.google.com/googleplay/android-developer/answer/9866151).
- **Microsoft Store.** Открой `9NXHRR2P4087` в [Partner Center](https://partner.microsoft.com/ru-ru/dashboard/products/9NXHRR2P4087/overview). Обнови MSIX и убедись, что он выбирается для нужного семейства устройств. Сверь `Identity` и четырёхкомпонентную версию с действующим пакетом, затем пройди все локализованные карточки, включая «Что нового». Сохрани, отправь на сертификацию и проверь, что опубликован нужный Submission. [Подготовка MSIX submission](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/create-app-submission?pivots=store-installer-msix), [скриншоты MSIX](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/add-screenshots-and-images).
- **Snap Store.** Проверь на Linux установку принятого Snap с действующими gates координатора. В аутентифицированной среде используй `snapcraft status revelation-x` и `snapcraft revisions revelation-x` (`list-revisions` в старых версиях). Если нужная проверенная ревизия уже есть, используй её, иначе загрузи принятый `.snap` через `snapcraft upload <absolute path>`. Дождись допуска и выпусти эту ревизию в `latest/stable` через `snapcraft release revelation-x <revision> latest/stable` или [страницу Releases](https://snapcraft.io/revelation-x/releases). Когда владелец поручает автоматически продолжить публикацию при следующем входе в Ubuntu, передай точный принятый кандидат через `scripts/local_release/snap-publication.json` и общий Linux-диспетчер. Сверь квитанцию с публичным каналом. Обнови [карточку](https://snapcraft.io/revelation-x/listing) и проверь показанные версию, канал и скриншоты. Если отдельного поля «Что нового» нет, добавь краткий блок обновления в описание. [Ревизии и каналы](https://documentation.ubuntu.com/snapcraft/9.0/how-to/publishing/manage-revisions-and-releases/).
- **Другие магазины.** Включай готовые и подключённые каналы по фактическим задачам и доступу. Новая регистрация или недоступный канал не должны задерживать готовые независимые площадки.

## Проверка результата

Записывай ссылку, пакет, версию и ID отправки каждого канала. Отличай сохранённый черновик, отправку на модерацию, одобрение и публичную доступность. По готовому каналу проверь публичную карточку, новые изображения, примечания, установку или обновление и загрузку данных. Сохрани один актуальный итог публикации и укажи оставшееся внешнее ожидание. При обычной модерации отслеживай результат в текущем чате с разумным интервалом. Для входа, ручного действия или недоступной среды уточняй только реальный блокер и продолжай остальные каналы. Передавай задачу на ревью по выполненным критериям проекта.
